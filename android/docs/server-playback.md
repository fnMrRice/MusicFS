# Android 与 Server 的连接和播放

本文是 Android 客户端的接入设计。手机、平板、电视和手表在各自设备上运行相同的协议适配代码，各自持有登录会话、播放队列和播放器。验收需要真实 Server 和设备。共同语义见[总体架构](../../docs/architecture.md)，接口定义由 [Server OpenAPI](../../server/docs/contracts/openapi.yaml) 维护。

## 登录与连接

连接页在前台通过 Android NSD 浏览 `_musicfs._tcp.`，按服务端广播填写 HTTPS 地址。用户可选择列表中的某台服务器，也可直接输入域名或 IP 和端口。服务从列表消失时保留用户正在编辑的地址；选中发现结果不会触发登录。协议与端口约定见[跨端连接协作](../../docs/architecture.md#7-本地连接退出与升级协作)。

1. 用户在本设备配置可达的 MusicFS HTTPS 地址，使用部署允许的 Origin 和显式输入的引导 Bearer 调用 `POST /api/v1/auth/session`。目前此入口创建管理员会话。手表提供同样的本机输入与登录流程，通过自己的 Wi-Fi 或可用蜂窝网络访问 Server。手机关机时也应能够完成首次登录。
2. 连接适配层按 Server 与登录会话隔离私有 Cookie，持有 CSRF 令牌。后续用 `GET /api/v1/auth/session` 检查会话、身份与有效期。普通查询使用会话 Cookie，HTTP 状态修改按契约附带 Origin 和 CSRF。引导 Bearer 只用于登录交换，提交后清除。若持久保存会话，使用 Android Keystore 保护加密密钥，退出时清除会话数据。凭据和授权流地址不进入日志。平台账号由 Server 的来源插件管理。
3. 用该会话的 Cookie、允许的 Origin 和子协议 `musicfs.control.v1` 升级 `/api/v1/control`，在 5 秒内发送含 CSRF 的 `auth` 首帧。收到 `ready` 后提交播放命令。首版按操作建立短连接，成功收到响应后关闭。后续长连接按协商间隔发送应用层心跳，并在收到 `capabilities.changed` 后刷新能力。
4. 退出时停止本机播放，使用仍有效的会话请求注销，关闭连接并清除凭据和用户缓存。离线时只能确认本机清理，远端撤销结果须据实展示。切换账号或实例时，旧连接返回的数据和音频不能进入新会话。Android 连接已部署的 Server，无需申请桌面启动器使用的本机租约。

登录和心跳的完整消息与错误处理见 [WebSocket 控制通道](../../server/docs/contracts/control-channel.md)。

## 原生播放协商

原生播放器声明 `capabilities.nativeHttp=true`，浏览器声明 `capabilities.htmlAudio=true`，请求只选其一。Server 使用 `outputProfile.transport` 返回所选传输。字段与校验分别见 [HTTP Schema](../../server/docs/contracts/http.schema.json)、[请求解码](../../server/src/app/api/playback.go)及[会话创建逻辑](../../server/src/playback/create.go)。

Android 首版上报 Media3 支持的 PCM WAV 与本机解码器支持的 MP3、FLAC 或 Opus/WebM。Server 按这些声明选择原流或处理后的输出。播放器校验返回的传输和流路径后，通过 OkHttp 读取；桌面原生播放器也可使用此契约。设备解码能力与耳机、电视音响的实际输出能力分别验证。

## 播放数据流

| 环节 | 协议和行为 |
| --- | --- |
| 选曲 | 四端通过 HTTP 查询本人可用的曲库和歌单。选择具体的 `sourceTrackId` 后，共享播放层发起创建请求。 |
| 创建 | 通过 WebSocket `request` 发送 `POST /playback/sessions`，附本次操作的幂等键、设备能力及偏好。消息内路径省略 `/api/v1`。成功后记录 `sessionId`、`attemptId`、`representationId`、有效期、输出描述和定位模式。 |
| 读取 | 将返回的 `streamUrl` 按配置的 Server 地址解析，校验同源、媒体路径及重定向目标。播放器的数据源仅向获准的同源地址发送对应会话 Cookie，流式读取 `proxy` 或 `processed` 输出。手表直接接收 Server 交付的音频，在表上解码并输出到已连接的耳机。 |
| 切歌与停止 | 让旧曲目的回调失效，取消读取，按会话标识经控制通道停止旧会话。若创建响应晚于切歌且仍可取得会话标识，只清理这个迟到会话。UI、遥控器和系统媒体控件使用同一设备内的播放命令入口。 |

首版为创建和停止分别建立短时鉴权控制连接，已发送的操作断线时不自动重放。持续心跳与能力订阅、以下定位和恢复策略及完整队列属于后续实现。

## 定位、恢复与断线

- `byteRange` 允许播放器在同一稳定表示上按范围读取。`timeRestart` 要求经 WebSocket 提交当前 `attemptId` 和整数毫秒的曲目位置；成功后丢弃旧缓冲，加载新流，用 `positionOriginMs` 映射回曲目时间。`none` 在应用界面及系统媒体控件中禁用定位。
- 共享播放层为每首曲目分配本机代次，串行执行该会话的定位和恢复。连续拖动或按遥控器时，先接收在途结果及新的 `attemptId`，再提交最新位置。前一首歌的结果不能覆盖新曲目的进度。
- 读取或解码失败时，提交当前尝试、实际观察到的错误及曲目位置。Server 决定同源恢复和重试预算。换源续播还需目标来源可用、录音关联正确、覆盖当前位置的时间轴证据及可定位输出。`continue` 按新描述继续；`promptRestart` 提供从头播放或取消。详细条件见 [Server 播放恢复](../../server/docs/playback/recovery.md)。
- 控制通道断开后有界重连、重新鉴权并刷新能力。已经发送而未确认的命令可能在服务端成功，连接层不自动重放。业务层显式重试时沿用原幂等键；无法确认当前尝试时停止自动控制，提示重新播放。媒体 GET 与控制连接分别跟踪，控制断线本身不足以判断本机已经停播。

## 联调验收

| 场景 | 通过条件 |
| --- | --- |
| 手表独立首次使用 | 手机关机，手表首次安装后通过可达网络输入服务地址与凭据，读取授权曲库，创建会话并向手表连接的耳机播放。 |
| 原生协商 | 用已验证格式与不支持的格式分别请求，核对实际选择的输出或错误；至少验证代理原流与需处理的输出各一例。 |
| 定位与恢复 | 三种定位模式分别符合描述；连续定位后切歌不会回跳；无时间轴证据时换源需要用户选择。 |
| 中断与隔离 | 在播放创建或定位响应前断网，再连接后无重复命令。撤销登录后验证旧凭据无法继续请求媒体。切换账号后验证新账号无法读取旧账号的媒体，迟到响应不再出现在当前界面。 |
