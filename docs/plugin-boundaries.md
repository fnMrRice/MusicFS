# C/S 插件职责与扩展边界

状态：架构细化；2026-10-11。本文定义跨端约束和实施顺序，不新增可调用 API、SDK 或已完成能力。精确接口归各实现仓库；事实基线见[总体架构](architecture.md)、[Server 架构](../server/docs/architecture.md)和 [Client 架构](../client/docs/architecture.md)。

## 1. 当前架构是否支持

支持继续扩展，但当前没有两端通用的即装即用插件系统。Server 已有 Go 宿主和独立插件进程，部分宿主固定校验内置插件身份/能力，新增插件 ID 仍需注册和适配；Client 已设计 Rust Plugin Host 与 C ABI，尚无可运行实现。Client 现确定为原生插件直接加载动态库，在同一原生宿主进程中运行；不采用插件 worker 或独立音频引擎进程。Windows 使用 DLL，其他目标平台使用 dylib/so。Client 不提供插件卸载，所有已加载库保留至进程退出，插件启停、更新和回滚统一重启生效。声明式主题不必包装为 DLL；Tauri/WebView 的系统进程结构不属于插件执行模型。

以下范围不能仅安装一个包就获得支持，实施前须先补契约或报告验证限制：

| 范围 | 当前限制 | 先完成的工作 |
| --- | --- | --- |
| Server 新插件 ID，包括同属 Provider 的适配 | 部分 Host 固定认可内置 ID/能力，并非读取任意 manifest 即注册 | 先补通用注册、配置与分派机制；核对方法覆盖，缺字段在 Server 修订 SDK 与样本 |
| NFS/SMB 直连、Bilibili/其他在线音频 | 现有播放资源通道仍有本地资源假设 | 扩展受授权资源读取、资产建档、版本/定位证据，不返回 NAS 凭据或任意代理 URL |
| Server 独立算法、输出存储等新插件角色 | 当前严格协议与注册表没有通用的任意角色机制 | 在 Server 先定义角色、宿主服务、能力和兼容迁移，再开发插件 |
| 任意 Server 音频节点组合 | 已支持有序、无状态、固定格式/帧数、零延迟/尾音的内置或外部 DSP；任意拓扑与有状态节点尚不支持 | 扩展排空、预滚和时间映射，逐能力验收 |
| Client 原生动态库 | 宿主、C ABI、安装包与平台加载尚待实施 | 按 C0—C3 实现加载、生命周期及最小 DSP 插件，C7 验证制品 |
| Client 原生播放协商 | 现有 Server 能力模型偏向 htmlAudio | Server 增加原生能力协商并回归旧 Web，Client 不冒报浏览器能力 |
| Client 原生插件故障隔离 | 同进程不能提供崩溃/内存破坏隔离或安全强停 | 接受宿主故障边界，验证受信任插件、可恢复配置和下次启动禁用；不回退为插件子进程 |

如果后续需求必须隔离恶意本机代码，或必须在插件卡死后强杀插件而保持 Client 运行，则与当前单进程约束冲突，应先向用户说明，不能静默改回多进程。普通接口缺失按已标明的设计增量处理，不宣称当前已经可用。

## 2. 尽量插件化的分工

“插件”指通过有版本契约替换实现的能力，不要求把每个类、线程或数据库表单独打包。一个插件包可以声明多个兼容能力，但能力、实例和配置分别标识；插件之间不直接链接对方私有接口，依赖由宿主解析，禁止循环依赖。

| 能力 | 所属端与插件方向 | 宿主保留的责任 |
| --- | --- | --- |
| 本地/挂载 NAS、直连 NAS、在线平台 | Server Music Provider；平台登录与远程歌单适配归对应 Provider | 授权、身份建档、扫描完整性、同步发布、用户与账号隔离 |
| 歌词、封面、标签候选 | Server 独立 Scraper；本地提取与各在线来源分别适配 | 候选选用、人工锁定、Media Store 发布、写回审批与恢复 |
| 解密、解复用、解码、DSP、编码与封装 | Server 音频插件；Client 按需要提供本机解复用、解码与 DSP | 链路选择、缓冲、时钟/映射、定位和实际效果报告 |
| 音频探测、指纹与候选评分算法 | Server 算法扩展，现有实现先保留，新角色需协议增量 | 证据版本、授权读取、人工排除、Recording 关联与续播决定 |
| 本机设备后端、歌词呈现、系统媒体控制 | Client 可替换的原生能力；新增 SDK 类型分阶段开放 | 唯一输出时钟、窗口/设备归属、命令验证、退出及回调释放 |
| 主题、可选外部控制 | Client 声明式主题、原生控制插件 | UI 数据接口、PlayerCore 状态与授权命令；普通控制不授予安装权限 |
| 数据库后端 / 备份 | Server 可信 Backend；数据库插件负责主库与实例状态库的建库、Schema、迁移和原子操作；内置 SQLite 与独立 SQLite Worker 已提供，其他数据库待适配 | 业务数据与事务契约、启动锁、生命周期、一致性清单、对象引用、密钥和恢复判断 |

各端插件类型及精确扩展契约分别见 [Server 插件架构](../server/docs/plugins/plugin-architecture.md)和 [Client 插件能力](../client/docs/plugin-capabilities.md)，不能把本表中的类别名直接写入现有 wire 协议。Web 继续按 Server 能力展示，不安装 C++ 插件，不读取 DLL，也不与 Server 插件通道直接通信。

以下职责保持内核模块：Server 的会话鉴权、API/事件协议及其 Schema 校验、稳定身份、业务数据与事务契约、人工结果保护、授权流网关和任务发布；Client 的 PlayerCore、Server 会话适配、安装/加载管理、配置提交、缓冲所有权、生命周期和受控启动器。可信存储后端负责具体数据库结构、初始化和迁移，成功后才返回可用后端；宿主取得数据锁后调用写入初始化，配置预加载只读且不建库。普通算法插件不能直接提交核心状态。外部 DSP 与持久化使用各自专用契约，细节见 [DSP 插件](../server/docs/plugins/dsp-plugins.md)和[存储插件](../server/docs/plugins/storage-plugins.md)。

## 3. 两端运行和语言选择

| 项目 | Client | Server |
| --- | --- | --- |
| 原生插件执行 | 单一 Rust 原生宿主进程内的动态库 | 按角色/任务受管的独立进程 |
| 边界 | 版本化 C ABI，固定宽度数据、不透明句柄、明确释放方 | 已有版本化 JSON-RPC/stdio 控制，任务授权的二进制数据通道 |
| C++ 构建产物 | CMake/C++23 动态库及运行依赖 | CMake/C++23 可执行插件；库封装留在其进程内 |
| 现有语言 | Rust 核心与原生适配可保留；主题/界面保留 TS/资源 | Go 宿主与现有 Go Worker 保留 |
| 故障范围 | 越界访问、崩溃或卡死可能影响整个 Client；超时不能撤销本机机器码执行 | 子进程可按期限回收；须撤销任务和数据通道，进程独立不等于 OS 权限沙箱 |
| 可复用对象 | 算法源码、测试向量、媒体格式语义 | 同左；SDK、生命周期和制品独立版本化 |

使用 C++ 的理由应明确到插件：例如现有原生库封装、DSP 算法或平台媒体 SDK。每个采用 C++ 的自有插件/适配层统一遵循 [CMake/C++23 规范](native-plugins.md)，不以 C++23 推导 ABI 通用性。第三方 C 库或原有工程保持其自身构建机制，由受控依赖集成；不为满足标准标记而改写上游源码。

## 4. 共同配置、能力与版本规则

1. 区分包 ID/版本/摘要、宿主 SDK/协议、角色接口、实例 ID、配置修订、装载代次和任务/播放代次。显示名不是身份；同包多角色不隐式共享账户或机密。
2. 包声明仅描述候选能力。目标平台和版本匹配、依赖可用、初始化成功并取得必要授权后，才发布运行能力。期望启用、已发现、待配置与已就绪分别呈现。
3. 新旧协议兼容按精确 Schema 与校验行为判定。当前 Server 严格解码不能假定未知可选字段总被忽略；需要配套升级时明确顺序、支持组合及回退范围。
4. 配置提交检查预期修订。热参数与需重建的参数分开，插件只提出配置结果，由宿主发布有效修订；失败保留原配置/原活动版本。凭据不进入包、主题、日志或普通导出。
5. 任务固定插件版本及配置摘要。Server 源资产或处理链改变输出表示时，重新协商并返回新 attempt/representation，Client 清理旧缓冲；Client 纯本地 DSP/设备图变化更新本机处理代次、图、缓存身份和效果快照，不要求 Server 重建不变的音频流。C/S 两端按有效处理链避免重复增益、EQ 或变速。
6. Server 停用只保存开关，重启后生效；当前业务准入、Worker 和已有租约保持，配置重建仍按自身契约排空。Client 停用只保存下次启动的期望开关并显示待重启，不立即改变当前运行能力；重启时不加载已停用插件。Client 更新/回滚同样下次启动激活，不提供包卸载或运行中卸载 DLL。两端正常任务取消都保留必要完成回调，不能把取消堵在未返回的串行业务调用之后；停用不删除音乐库、歌单、人工内容或实例数据。

Client 同进程加载使原生插件具有访问宿主地址空间的能力。受限 API 与清单用于防止误用和记录约定，不能声称隔离恶意插件；安装与更新需明确可信来源。Server 的宿主授权检查保护核心接口，但 OS 沙箱能力仍须按平台单独验证。

## 5. 实施顺序与验收

| 顺序 | 工作 | 完成证据 |
| --- | --- | --- |
| A | 梳理现有方法/能力与新增接口，分别形成两端 SDK 草案；Server 将按内置 ID 的注册与分派改为版本化注册/能力契约 | 每项有宿主、输入/输出、资源权限、取消与版本策略；身份与可信来源校验保留，不改变现有 wire 名称含义 |
| B | Client 最小动态加载链；Server 最小 C++ IPC 插件 | CMake/C++23 干净构建；正确产物完成 C ABI/IPC 往返，坏版本与缺依赖拒绝；不是空入口成功 |
| C | 安装、能力注册、配置、停用与更新 | 新包无需重编译宿主；Client 启停/更新/回滚一律重启生效、已加载库保留到退出，Server 按自身管理契约应用；失败可恢复 |
| D | 扩展来源/媒体算法/设备等能力 | 逐角色验收正确结果、时钟、背压与身份；真实资源失败不破坏已发布状态 |
| E | C/S/Web 联合回归和发行 | 原流、处理流、seek/recover、配置/能力变化和旧 Web 兼容；制品支持矩阵与证据一致 |

最小故障矩阵包括：错误 target/ABI、未知必需能力、半途取消、回调迟到、插件拒绝退出、错误配置、依赖缺失、崩溃后重启、更新失败和恢复旧包。Client 崩溃注入在可丢弃测试运行中验证下次启动恢复，不能以主进程存活作为单进程插件崩溃隔离验收；Server 才验证 Worker 崩溃后的回收和无关实例继续服务。

Client 与其余扩展仍按设计实施；Server 的 DSP/持久化增量及验证在对应实现仓库维护。实现提交完成后再由主仓库记录子模块版本。运行边界见 [PlantUML 源图](diagrams/plugin-boundaries.puml)。
